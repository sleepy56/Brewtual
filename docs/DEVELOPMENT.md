# Brewtual development guide

For a first local run, start with the [README](../README.md#run-locally).

## Application structure

Next.js and TypeScript host the website and `/api/v1` API in one application. React Native and Expo provide the separate Android/iOS client under `mobile/`. Both use the same PostgreSQL database through Prisma. The active server uses ordinary TypeScript services; it has no NestJS runtime or custom Express server.

The website includes the public landing page, a personal task/Daily/Goal planner, separate partner and group token markets, previous partner habits and rewards, friend circles, and an installable phone experience. The separate Expo client retains its partner screens and deliberate fictional demo; the new friend-circle interface is currently on the website.

| Location | Purpose |
| --- | --- |
| `app/page.tsx`, `app/verify-email/page.tsx` | Website entry pages |
| `src/web/landing.tsx` | Public homepage and interactive sample checklist |
| `src/web/pair-habits.tsx`, `src/web/client.ts` | Account flow, partner screens, and browser API transport |
| `src/web/planner.tsx`, `src/server/planner/` | Personal planning, token approvals, per-space markets, and ledgers |
| `src/web/connections.tsx` | Circle goals, invites, cheers, and milestone promises |
| `src/web/install-app.tsx`, `app/manifest.ts`, `public/sw.js` | Installation controls, app manifest, and offline fallback |
| `app/api/v1/[...path]/route.ts` | Next.js Node API entrypoint |
| `src/server/api.ts`, `src/server/schemas.ts` | Routing, input validation, cookies, rate limits, and safe errors |
| `src/server/auth`, `pairs`, `goals`, `rewards`, `wallet`, `circles` | Server business logic |
| `src/server/services.ts` | Explicit service construction and dependencies |
| `prisma/` | Database schema and additive migration history |
| `mobile/` | Separate Expo phone client |

## Local configuration

Use Node 24.9 or newer within Node 24. `npm run local:setup` creates a root `.env` from [the example](../.env.example) with a random signing key and preserves an existing file. Next.js and Prisma read the root environment file. Old environment files under `backend/` are no longer loaded; transfer any needed settings into the root `.env` yourself. Never commit secrets.

The supplied Docker Compose database listens on port 5433. Its default credentials and database name match `.env.example`. If you choose a different PostgreSQL database, update `DATABASE_URL` and `DATABASE_URL_UNPOOLED` before running migrations.

For browser signup and login locally, use:

- `AUTH_MODE=jwt` and a strong `JWT_SECRET` (generated by local setup).
- `APP_WEB_URL=http://localhost:3000`.
- `CORS_ORIGINS=http://localhost:3000,http://localhost:8081`.
- `REQUIRE_EMAIL_VERIFICATION=false`, or omit it until email delivery is configured.

The default signup flow needs no SMTP and sends no email. Optional verification and development token mode are described in the [authentication guide](AUTHENTICATION_PLAN.md).

After pulling schema changes, run `npm run db:generate` and `npm run db:migrate`. Friend circles require `20261023170000_friend_circles`, and personal planning requires `20261023190000_personal_planner`; an existing database must receive it too. No database reset is needed.

## Running the clients

`npm run dev` starts the website and API together. `npm run build` followed by `npm start` runs a production build. Production JWT configuration requires an exact HTTPS `APP_WEB_URL`; use the development server for ordinary HTTP local work.

For Expo, set `EXPO_PUBLIC_API_URL` in `mobile/.env` to a reachable API base ending in `/api/v1`, then run `npm run mobile` separately. A physical phone needs your computer’s LAN IP or the deployed HTTPS API; `localhost` on the phone points to the phone itself. Restart Expo after environment changes. `npm run mobile:web` is an optional Expo browser preview, separate from the Next.js website.

See the [Expo guide](../mobile/README.md) for native client details and the [deployment guide](DEPLOYMENT_AND_MOBILE_PLAN.md) for installing the website on a phone.

## Checks

| Command | Coverage |
| --- | --- |
| `npm test` | Server unit/API, browser transport, and personal-planner component tests |
| `npm run typecheck` | Prisma generation, Next.js route types, and TypeScript |
| `npm run mobile:test` | Expo transport, mapping, calendar, and mutation-failure tests |
| `npm run mobile:typecheck` | Expo TypeScript checks |
| `npm run test:vercel` | Production build and real server routing smoke test |
| `npm run test:integration` | Real local PostgreSQL transactions in an isolated test schema |

The production smoke check starts the actual Next.js server with Lambda-style module restrictions. It checks website pages, API health, auth validation, and website availability during a database outage.

Integration tests require `TEST_DATABASE_URL` pointing to local PostgreSQL. They create and remove isolated schemas, reject remote database URLs, and use fictional accounts for signup, verification, and partner habit/reward flows. Planner integration tests also connect a partner and two groups, check separate balances, concurrent awards and spending, private notes, and ledger constraints. They do not access Neon or send real email. Circle service tests additionally cover goal ownership, expired/consumed codes, reusable group codes, and partner capacity.

## Troubleshooting

- **Windows build fails while creating junctions:** if Turbopack cannot create file links in a restricted environment, use `node node_modules/next/dist/bin/next build --webpack` with Node 24. The routing check can then run separately with `node --test test/vercel-routing.test.cjs`.
- **Website opens but account or shared progress fails:** check database configuration, connectivity, and pending migrations. `/api/v1/health` checks the server; `/api/v1/health/ready` also checks the database.
- **A phone cannot reach the local API:** use the computer’s LAN IP instead of localhost, confirm the server is reachable, and restart Expo after changing its environment.

## Naming compatibility

The product name is **Brewtual**. Existing package IDs, database names, phone URL scheme, saved theme keys, and account/session identifiers retain their original internal names so existing environments and saved preferences continue to work. The website, home-screen installation, Expo display name, and verification email subject use the Brewtual brand.
